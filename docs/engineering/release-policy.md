# Client release and rollback policy

Both client apps share one canonical release identifier based on the release boundary in America/Los_Angeles:

`YYYYMMDD-HHMM`

Example: `20261022-0937`.

The build wrapper derives bundle-compatible values without losing the canonical ID:

- `KidsReleaseVersion`: `20261022-0937`
- `CFBundleShortVersionString`: `2026.10.22`
- `CFBundleVersion`: `202610220937`
- Git tag: `client-v20261022-0937`

Two releases in the same minute are prohibited. Wait for the next minute rather than adding an undocumented suffix.

## Release record

Each release has `releases/client/<version>/manifest.json` containing:

- canonical release and bundle versions;
- source branch, full commit ID, immutable tag, and implementation SHA-256;
- deterministic hashes and sizes for the tvOS and iOS artifacts;
- hashes for the QA reports used at the gate;
- the previous release version, commit, and tag used for rollback;
- the Agent Mail thread and delivery record used to notify GreenCastle.

The manifest is generated by `Scripts/Kids/release_metadata.py`; do not hand-edit hashes.

## Candidate procedure

1. Confirm the canonical Bead, review the source diff, and make the candidate source commit.
2. Generate the version with `python3 Scripts/Kids/release_metadata.py version`.
3. Build each affected scheme through `Scripts/Kids/build_with_revision.py --release-version <version> -- ...`. The wrapper embeds the deterministic source digest and refuses acceptance if source changes during the build.
4. Verify each built app's `KidsReleaseVersion`, `CFBundleShortVersionString`, `CFBundleVersion`, and `KidsEvidenceImplementationRevision` before installation.
5. Run the QA policy gate against those exact artifacts. P0/P1 must be clear.
6. Notify GreenCastle over Agent Mail with the version, source commit/digest, artifact hashes, compatibility notes, rollout state, and rollback target. Use the release Bead as `thread_id`; require acknowledgement only for a real compatibility or rollout transition.
7. Generate the manifest, commit it, create the immutable tag, and push the branch and tag.
8. Record deployment target and health state in the Bead. A built candidate is not a deployed release.

## Rollback

Rollback is supported only to the predecessor named in the manifest.

1. Stop the rollout and notify GreenCastle with the failed release, symptom, affected surface, and whether backend health is implicated.
2. Verify the predecessor artifact hash against its manifest and reinstall that artifact.
3. Preserve app data, authentication state, journals, history, approvals, pending work, backend databases, and media. Rollback never authorizes a reset.
4. Verify launch, sign-in state, one safe read path, and the specific failed surface.
5. Record the rollback time, target version, observed result, and Agent Mail message ID in the Bead. Fix forward with a new minute-based version.

## Health communication

BlueLake sends GreenCastle a changed-state message for a client release, rollback, client-visible backend health alert, or compatibility blocker. GreenCastle receives concise release/version/hash/impact/next-action fields. Routine unchanged health and acknowledgements are not sent.
